# 项目通用规则

- 所有文档、源码注释、提交说明中的项目说明性内容默认使用中文。
- 所有文件必须保持 UTF-8 编码。
- 设计文档必须同时维护一份英文翻译副本。
  - 中文设计文档示例：`xxx-design.md`
  - 英文副本示例：`xxx-design.en.md`
- 不要生成乱码，不要使用 GBK 编码保存文件。

# 设计变更流程

- 修改设计方案前，必须先给出修改建议并等待用户确认。
- 未确认前，不允许直接修改设计文档。
- 更改代码前，必须先同步更新设计文档。
- 如果代码实现与设计文档不一致，优先提示风险，不要直接硬改。
- 对接口、协议、数据库结构、状态机、任务流程的修改，必须先说明兼容性和回滚影响。

# Java 注释规则

- 所有 public/protected 接口和类必须有中文功能性说明。
- 所有方法除了 getter/setter 外，都必须有中文简要说明。
- 关键实现逻辑必须添加中文实现说明。
- 注释要解释“为什么这么做”和“关键约束”，不要只复述代码。
- 不要为明显代码添加废话注释。
- 注释风格优先使用 JavaDoc。

# 类注释要求

每个接口和类至少说明：

- 这个类/接口负责什么
- 在整体流程中的位置
- 重要约束或线程安全要求
- 是否涉及远程调用、事务、锁、磁盘、网络或 Raft

# 方法注释要求

除 getter/setter 外，每个方法至少说明：

- 方法用途
- 关键参数含义
- 返回值含义
- 重要异常或失败场景
- 是否有副作用

# 关键实现注释要求

以下场景必须写实现说明：

- 分布式一致性
- Raft 提交或读取
- 事务/MVCC/锁
- RocksDB/LevelDB 迭代器和资源释放
- 网络连接、SSH、HTTP、超时、重试
- 磁盘分区、格式化、挂载、rsync
- 状态机流转
- 幂等、恢复、回滚
- 并发控制
- 数据兼容和升级迁移

# 修改代码前的固定动作

执行任何代码修改前，必须先：

1. 搜索相关设计文档。
2. 判断是否需要更新设计文档。
3. 如果需要，先提出设计文档修改建议。
4. 等待用户确认后，再修改设计文档。
5. 设计文档更新后，才能修改代码。
6. 修改代码后，说明涉及文件、验证方式和潜在风险。

# 输出偏好

- 默认用中文回复。
- 复杂任务先给实施计划。
- 不要把不相关命令混在一起。
- 给排查命令时，每条命令说明目的。
- 对破坏性命令必须明确标注风险。
